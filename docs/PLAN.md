# 麻将联机游戏实施计划

## 1. 目标与首版边界

首版交付一个可运行、可测试、可继续扩展的四层系统：Vue 客户端、REST/WebSocket 接口、房间/对局服务、可插拔规则引擎。玩家可创建或加入多个独立房间，准备后自动开局，进行摸牌和打牌，并按房间规则决定结束后留房或退出。

首版内置经典四人规则与双人快速规则，支持自定义人数、牌组、起手牌数、圈数、胡牌型、计分参数、结束条件及结束后行为。地方役种、吃碰杠、断线重连与持久化牌谱作为后续规则插件，不与房间核心耦合。

## 2. 用户流程

1. 玩家输入昵称进入大厅，查看实时刷新房间列表。
2. 创建房间时选择内置规则或编辑全部规则参数；也可输入房间号加入。
3. 房内玩家准备；人数达到规则要求且全部准备后自动开始。
4. 当前玩家摸牌、选择手牌打出；服务端是牌局状态唯一可信来源。
5. 达成胡牌条件时可胡牌；牌墙耗尽则流局。
6. 结算后根据规则自动退出，或保留在房间等待下一局。

## 3. 架构与关键决策

- 后端：Java 21、Spring Boot、REST、STOMP WebSocket；内存仓储便于首版运行，仓储接口预留数据库替换点。
- 前端：Vue 3、TypeScript、Vite、Pinia；自适应桌面/移动布局。
- 实时模型：写操作使用 REST 获得明确错误；房间状态通过 `/topic/rooms` 与 `/topic/room/{id}` 广播。
- 并发：每个房间的状态变更在服务端同步执行，防止重复准备、越权出牌和同一牌被打出两次。
- 隐私：REST/广播状态按观察者裁剪，其他玩家手牌只返回张数。
- 规则：`RuleSet` 是房间级不可变快照，`WinningRule` 接口承载胡牌算法，新增地方规则无需修改房间生命周期。

## 4. 数据与规则

`RuleSet` 包含人数、牌型集合、每种牌数量、起手牌数、圈数、允许胡牌型、基础点、番上限、自摸倍率、流局/目标点/圈数结束条件和结算后行为。服务端校验所有规则边界，拒绝无法发牌或无胡牌型的配置。

状态机：`WAITING -> PLAYING -> FINISHED`；留房规则会在结算后归一为 `WAITING`，退出规则删除房间。对局内严格校验当前玩家、摸/打顺序和手牌所有权。

## 5. 安全与异常

- 服务器生成房间号和玩家 ID，输入长度及规则范围均校验。
- 不信任客户端牌面、分数或回合信息；客户端只提交动作及牌 ID。
- 统一错误响应包含错误码和可展示消息。
- 离开导致人数不足时终止当前对局并回到等待态。

## 6. 实施顺序

1. 建立文档、目录和构建配置。
2. 完成规则模型、胡牌判定、对局引擎与房间服务。
3. 完成 REST/WebSocket 接口和异常处理。
4. 完成大厅、建房规则编辑器、等待房和牌桌。
5. 添加单元、集成及前端测试，执行构建并记录结果。

## 7. 验收标准

- 可同时创建多个房间，玩家只能操作自己所在房间。
- 满员全准备自动开始；非法动作返回 4xx 且不改变状态。
- 两种内置规则可选，自定义规则经校验后成为房间快照。
- 摸牌、打牌、轮转、胡牌/流局与结算后行为可运行。
- 其他玩家手牌内容不泄露。
- 后端测试、前端测试和生产构建全部通过；结果写入 `docs/TEST_REPORT.md`。

## 9. 规则中心改版（2026-08-20）

### 页面职责

- 建房弹窗只负责牌局名称和规则选择，并提供“查看规则详情”“前往规则中心”入口。
- 规则中心是独立应用页面，左侧展示内置与自定义规则库，右侧展示详情或编辑副本。
- 内置规则只读；用户可复制任意规则后修改并以新名称保存。房间始终保存选中规则的完整快照。

### 声明式自定义和牌型

每个自定义和牌型由基础结构和约束组合而成，而不是执行用户脚本：

- 基础结构：四面子一雀头、七对子。
- 番值：1–100 番，结算时仍受房间封顶番限制。
- 花色要求：不限、清一色（仅一种数牌花色）、三色齐全。
- 字牌策略：允许、必须包含、禁止。
- 数牌范围：最小点数与最大点数。
- 刻子限制：可要求标准牌型全部由刻子组成。

这种声明式模型能组合出清一色、混一色、断幺、全带字、对对和等大量规则，同时避免上传代码带来的安全问题。后端对每个自定义牌型重新验证并实际参与和牌及番值计算。

### 规则目录接口

- `GET /api/rules`：列出内置与已保存的自定义规则。
- `POST /api/rules`：校验并保存自定义规则；名称唯一。
- `PUT /api/rules/{name}`：更新同名自定义规则。
- `DELETE /api/rules/{name}`：删除自定义规则，内置规则不可删除。

首版规则目录仍使用进程内存；后续替换数据库时保持接口不变。

## 10. M2-A 弃牌响应与基础副露（2026-08-20）

### 本阶段范围

- 弃牌和（放铳），按非自摸倍率结算并只向出牌者收取点数。
- 碰、吃、弃牌明杠；玩家公开副露及来源对所有人可见。
- 每套规则可分别启用或关闭放铳、吃、碰、杠。
- 弃牌响应窗口与“过”操作；无任何可响应玩家时自动进入下一玩家摸牌。
- 操作优先级：和牌高于杠/碰，杠与碰高于吃；同优先级按出牌者之后的座次距离决定。

### 状态与校验

1. 玩家弃牌后，服务端计算其他玩家实际可执行的操作。只有至少拥有一个操作的玩家进入响应集合。
2. 响应窗口存在时暂停摸牌、出牌和自摸；候选玩家提交操作或“过”。所有候选响应后一次性裁决，避免请求先后顺序改变规则结果。
3. 吃仅限出牌者的下一家、仅限数牌；客户端提交两张手牌 ID，服务端重新验证顺子。
4. 碰自动消耗两张同牌，明杠自动消耗三张同牌并补摸一张；被使用的牌从出牌者弃牌区移除。
5. 暗手基准张数按 `起手张数 - 3 × 副露数` 计算。正常摸牌、吃碰后的出牌以及杠后补摸均据此校验。
6. 和牌判定使用“暗手 + 副露结构 + 当前弃牌”组成完整牌型；已有副露时不能按七对子和牌。

### 后续增量

- M2-B：暗杠、加杠、抢杠和、杠上开花与海底牌。
- M2-C：多人同时和牌策略、响应倒计时、超时自动过与托管。

## 11. M2-B 杠牌扩展与末张和牌（2026-08-20）

### 实施顺序

1. 暗杠：当前玩家正常摸牌后，四张相同暗手可组成暗杠并立即补牌。
2. 加杠：当前玩家正常摸牌后，可以用第四张同牌将自己的碰升级为杠。
3. 抢杠：加杠先进入仅允许“抢杠和/过”的响应窗口；无人和牌才正式升级副露并补牌。
4. 杠后补牌：补牌后保持当前玩家出牌权；补牌和牌标记为“杠上开花”。
5. 末张牌：正常摸到牌墙最后一张后自摸标记“海底捞月”；该牌被打出后其他玩家和牌标记“河底捞鱼”。

### 规则与计分

- 规则可分别启用暗杠、加杠和抢杠。
- 杠上开花与海底/河底的附加番分别配置，默认各 1 番，仍受房间封顶番限制。
- 暗杠副露对外显示四张牌，但首版暂不隐藏中间两张；牌谱权限完善后再区分拥有者与旁观者视图。
- 加杠响应期间暂停摸、打、自摸和其他杠操作。抢杠成立时第四张牌交给和牌判定，原碰保持不变；无人抢杠才消耗第四张牌并升级副露。
- 本阶段继续采用单一和牌者：多个玩家均可抢杠时，按杠牌者之后最近座次裁决。多人同时和牌由 M2-C 的房间规则处理。

### 明确边界

- 不实现国士无双抢暗杠、杠宝牌、王牌区与岭上牌独立牌堆。
- 不实现响应倒计时和超时托管，仍由候选玩家主动“过”。

## 12. M2-C 多人和牌与响应托管（2026-08-20）

### 实施顺序

1. 多人和牌策略：房间规则可选择“一炮多响”或“截和”；截和仍由出牌者之后最近座次获胜。
2. 多人结算：一炮多响时，每位合法和牌者分别获得完整荣和点数，出牌者承担各家的合计点数；抢杠和使用同一策略。
3. 响应倒计时：弃牌与加杠响应窗口携带服务端截止时间，所有客户端显示同一个剩余秒数。
4. 超时自动过：截止后服务端将仍未响应的候选玩家记为“过”，立即执行正常优先级裁决，避免牌局永久卡住。
5. 响应托管：玩家可在房间中打开“响应托管”；后续出现吃、碰、杠、荣和或抢杠候选时服务端直接代为过牌，不依赖客户端在线。

### 状态、并发与兼容

- `responseTimeoutSeconds` 为 0 时关闭倒计时，允许范围为 0–120 秒；内置规则默认 15 秒。
- 截止时间由服务端生成并随房间视图返回。定时任务只在房间锁内补齐尚未响应的玩家，和手动响应共用同一裁决函数，确保不会重复结算。
- 一炮多响只收集已选择“和”的合法候选；碰、杠、吃仍按原优先级在没有任何和牌者时裁决。
- 房间视图保留 `winnerId` 作为首位赢家兼容字段，并新增 `winnerIds` 表示完整赢家列表。
- 响应托管仅代为处理响应窗口，不自动替玩家摸牌或出牌；完整机器人托管留到 M4。

### 验收标准

- 固定三人牌例分别验证一炮双响、截和、双抢杠、多人计分与赢家列表。
- 固定时间点验证弃牌和加杠窗口超时后自动过牌，已提交响应不会被覆盖，超时任务重复执行不重复结算。
- 浏览器验证规则中心配置、房间详情、倒计时显示、托管开关及实际超时后自动轮转。
- 后端、前端测试与生产构建全部通过，执行结果更新至测试矩阵和测试报告。

### 后续边界

- M2-D 再实现王牌区、独立岭上牌堆、杠宝牌与对应牌桌展示。
- 一炮多响仍以同一张弃牌分别计分，不实现包牌、责任支付或流局满贯等地方责任规则。

## 13. M2-D 王牌区、岭上牌与宝牌（2026-08-20）

### 可选规则模型

新增独立 `DeadWallRules`，默认关闭，非日式玩法不受影响：

- `enabled`：是否启用王牌区与独立岭上补牌。
- `size`：开局从牌墙尾部预留的王牌张数，允许 4–20，默认 14。
- `replacementTileCount`：王牌中可用于杠后补牌的岭上牌数量，允许 1–4，默认 4。
- `doraEnabled`：是否启用宝牌。
- `initialIndicators`：开局翻开的宝牌指示牌数量，允许 0–5，默认 1。
- `revealIndicatorAfterKong`：每次成功完成杠牌后是否再翻一张指示牌。
- `doraFanPerTile`：每张命中宝牌增加的番数，允许 0–10，默认 1。

### 牌墙与补牌语义

1. 开局洗牌后先从牌墙尾部预留王牌，再向玩家发牌；客户端的“牌墙余张”只统计可正常摸取的活牌墙。
2. 王牌中的前若干张组成独立岭上补牌堆，后续最多五张组成宝牌指示牌池，其余为本阶段不使用的保留牌。
3. 明杠、暗杠、加杠成功后只从岭上补牌堆补牌，不再从活牌墙取牌；抢杠成立时不消耗岭上牌，也不新增杠宝牌。
4. 岭上牌耗尽后再杠会以“无岭上牌可补”流局；不开启王牌区时保持原有普通牌墙补牌逻辑，保证已有自定义规则兼容。
5. 岭上补牌不同时算作海底牌；仍可按房间规则判定杠上开花。

### 宝牌与计分

- 数牌指示牌按 1→2→…→9→1 循环；风牌按东→南→西→北→东循环；三元牌按白→发→中→白循环。
- 宝牌只在手牌已经满足允许和牌型后附加番，不能单独赋予和牌资格。
- 每张实际手牌和副露牌都会按所有已翻开的指示牌计数；杠副露的第四张牌也计宝牌。
- 和牌消息展示宝牌附加张数/番数，最终番数继续受房间封顶番限制。

### 验收标准

- 固定牌堆验证开局预留王牌、活牌墙张数、岭上补牌不消耗活牌墙、最多四次补牌和关闭功能时的兼容路径。
- 固定牌例验证数牌、风牌、三元牌循环，手牌/副露/杠第四张宝牌计数，以及宝牌不能让错误牌型和牌。
- 验证每次成功杠牌新增指示牌，抢杠和不新增指示牌。
- 浏览器验证规则中心配置、牌桌王牌/岭上余量、指示牌与对应宝牌展示。
- 完成后端、前端自动化测试、生产构建与测试报告归档。

### 后续边界

- 暂不实现里宝牌、赤宝牌、四杠散了、从活牌墙补回王牌以恒定保持 14 张等更细的日麻牌墙规则。
- 地方玩法中的财神、混儿和花牌仍应使用独立规则插件，不复用日式宝牌定义。

## 14. M2-E1 可累计番种引擎与结算明细（2026-08-20）

浏览器边界验收同时要求：只有当前手牌确实命中允许的和牌型并达到最低番时，牌桌才开放“自摸”按钮。
自动退出房间的自摸、荣和与抢杠和均须在结算成功后清理本地身份并返回大厅，不显示过期房间错误。

### 本阶段目标

把当前“所有命中牌型只取最高番”的单值判定升级为结构化计分结果，为后续国标、日式规则包提供统一基础。本阶段不一次性内置全部地方番种，而是先完成累计、门槛、互斥和可解释结算。

### 计分规则模型

新增独立 `ScoringRules`：

- `cumulativePatterns`：关闭时保持旧行为，只取最高番；开启时累计所有未被排除的命中番种。
- `minimumPatternFan`：和牌所需的最低“番种番”，允许 1–100；宝牌、杠上开花和海底等附加番不用于满足门槛。
- `includeBasePatternFan`：自定义番种命中时，是否仍累计其基础结构（四面子一雀头/七对子）的番值。
- `exclusions`：由“高阶番种 ID → 被覆盖番种 ID”组成的列表；两者同时命中时只保留高阶番种。

默认配置为不累计、最低 1 番、不额外累计基础结构、无互斥关系，确保已有规则与得分保持兼容。

### 结构化计分流程

1. 使用暗手、和牌张和每个副露的前三张构成基础和牌结构，分别计算内置与自定义番种命中项。
2. 根据累计开关选择最高项或全部项，再应用基础结构策略和显式互斥关系。
3. 只有保留番种的合计达到 `minimumPatternFan` 才具备和牌资格；宝牌与特殊状态不能补足最低门槛。
4. 取得和牌资格后再追加宝牌、杠上开花、海底/河底等计分项，最后应用封顶番。
5. 每个赢家保存独立结算：番种明细、原始番、封顶后番、得分、自摸/荣和与支付者。多人和牌产生多份结算。

### 前端与兼容

- 规则中心提供累计开关、最低番、基础结构番和互斥关系编辑器。
- 牌局结束留房时展示每位赢家的完整结算清单；`winnerId/winnerIds` 和原消息字段继续保留。
- 旧客户端未提交 `ScoringRules` 时由服务端使用兼容默认值。

### 验收标准

- 固定牌例验证旧规则最高番行为不变，以及累计开启后的多番种求和。
- 验证显式互斥移除低阶番、基础结构番开关和最低番门槛。
- 验证宝牌与特殊番不能满足最低番，但合法和牌后会出现在结算明细中。
- 验证自摸、荣和、一炮多响分别生成正确的赢家结算和支付信息。
- 浏览器验证规则编辑、房间规则摘要和真实和牌后的结算明细展示。

### 后续阶段

- M2-E2：基于该引擎提供国标基础规则包与日式基础规则包。

- `playerId` 继续作为公开座位标识，`resumeToken` 使用安全随机数生成并只在创建、加入、恢复响应中返回。
- Controller 在进入 `RoomService` 动作前统一调用常量时间令牌校验；缺失、错误或其他玩家令牌均返回无权操作。
- `RoomSnapshot`/`PlayerSnapshot` 只用于存储层，显式列出全部可变字段，不直接反序列化领域对象，避免构造器和集合不变量被绕过。
- 每次房间广播前保存全部房间快照；空房间、自动解散和离开时同步删除。临时文件写完后原子替换正式文件。
- 恢复时重建牌墙队列、玩家集合及响应窗口；已过期的响应窗口由现有定时任务在下一次扫描时处理。
